# CLAUDE.md — FourD Slicer Service

Headless-сервіс нарізки 3D-моделей. Викликач надсилає сюди 3MF і отримує назад, скільки грамів кожного філаменту піде на друк, скільки всього кольорів і скільки триватиме друк. Типове застосування — розрахунок собівартості друкованого товару.

Цей файл — довга пам'ять проєкту: **чому** все влаштовано саме так і на які граблі вже наступали. Коротке введення й опис API — у `README.md`.

Сервіс **нічого не знає про свого викликача**: на вході файл і назви профілів, на виході грами, метри, вага, час і плити. Ні артикулів, ні цін, ні товарів. Перший споживач — інтернет-магазин на Magento, але в коді від цього немає нічого.

## Чому саме upstream OrcaSlicer, а не Snapmaker Orca

Спочатку планувався форк Snapmaker Orca — здавалося логічним, бо друкуємо на Snapmaker U1. **Він непридатний.** Його CLI падає з SIGSEGV на будь-якому 3MF-проєкті:

```
Slic3r::GUI::GUI_App::filaments_cnt() const          <- SIGSEGV
  <- Slic3r::GUI::expand_plate_extruders(...)
  <- Slic3r::GUI::PartPlate::get_extruders_under_cli(...)
  <- Slic3r::CLI::run(int, char**)
```

CLI-гілка звертається до синглтона GUI-застосунку, якого в headless-режимі не існує. Перевірено на версіях 2.3.4 (flatpak) і 2.3.5 (Docker), з одним філаментом і з трьома, з підстановкою профілів і без — падає завжди, обійти прапорцями неможливо.

Upstream OrcaSlicer нарізає ті самі файли успішно **і теж несе профілі Snapmaker U1** (`resources/profiles/Snapmaker/` — 7 машинних, 49 process, 38 філаментних із позначкою `@U1`). Тобто єдина причина триматися за форк відпала.

Побічна знахідка: `--load-settings` із системними профілями (у яких є `inherits`) валить форк окремо — CLI очікує вже «сплющений» профіль, без успадкування.

## Репарація вхідного 3MF — обов'язкова

Файли з MakerWorld — це проєкти Bambu Studio, і слайсер OrcaSlicer-родини їх без правок не завантажує. `repair3mf.py` лагодить дві речі:

1. **`Metadata/project_settings.config`** — п'ять ключів зі значеннями поза схемою: `wall_filament`, `sparse_infill_filament`, `solid_infill_filament` (`0` → `1`), `raft_first_layer_expansion`, `tree_support_wall_count` (`-1` → `0`). Без цього — `wall_filament: 0 not in range [1,2147483647]` і вихід.
2. **`Metadata/filament_settings_*.config`** — літеральні рядки `"nil"` у масивах (`"nozzle_temperature": ["210","nil"]`) і `inherits` на пресет Bambu, якого поза Bambu Studio не існує. Без цього — `Deserializing nil into a non-nullable object`.

**Видаляти вбудований конфіг не можна.** Без `project_settings.config` слайсер падає ще раніше, ніж доходить до файлу. Тому підхід «вирізати профіль Bambu і підставити свій» не працює — тільки точкова репарація.

Репарація застосовується автоматично в `OrcaSlicerEngine.preprocess()`; файли без `project_settings.config` проходять без змін.

## Машинні налаштування чужого принтера — і чому нарізка профілем U1 падала

3MF із MakerWorld несе налаштування **тієї машини, на якій його зробив автор**, і вони переживають `--load-settings`: наш профіль накладається зверху, але значення всередині `project_settings.config` лишаються. Здебільшого це нешкідливо, але деякі комбінації Orca відхиляє.

Файли з Bambu-родини кажуть `single_extruder_multi_material = 1` (одне сопло, до якого AMS по черзі подає чотири філаменти). Профіль процесу U1 вмикає `ooze_prevention = 1`, а Orca дозволяє це лише коли прапорець вимкнено. Нарізка вмирає так:

```
exit_code 205
run found error, return -51, exit...
Ooze prevention is only supported with the wipe tower
when 'single_extruder_multi_material' is off.
```

**Друге речення раніше не було видно.** Orca пише хід роботи в stdout, а причину відмови — у stderr; `_run()` віддавав тільки stdout, тож назовні йшло беззмістовне `return -51`. Тепер `_log()` склеює обидва потоки — саме тому цей діагноз узагалі вдалося поставити.

Виправляє це `_machine_overrides()`: коли передано `machine_profile`, машинні налаштування беруться **з нього** і підмінюються у `project_settings.config` (одним проходом усередині `repair()`, щоб не перепаковувати десятки мегабайт меша вдруге).

**Значення береться з профілю, а не з константи** — і це не педантизм. Для U1 правильний нуль (тулченджер, чотири незалежні голови), для Bambu A1 — одиниця. Зашити будь-яке з них означало б зламати другий принтер тоді, коли він з'явиться в парку:

```
Snapmaker/machine/Snapmaker U1 (0.4 nozzle)   -> {'single_extruder_multi_material': '0'}
BBL/machine/Bambu Lab A1 0.4 nozzle           -> {'single_extruder_multi_material': '1'}
(без machine_profile)                         -> {}
```

`_profile_setting()` йде за `inherits`, і **виграє найближче визначення** — як робить і сама Orca. Ланцюг U1 це показує наочно: `fdm_klipper` і `fdm_toolchanger` ставлять `1`, і лише `fdm_U1` повертає `0`. Успадковані профілі лежать у тій самій теці, що й листовий.

Список таких налаштувань — `OrcaSlicerEngine.MACHINE_SETTINGS`; поки в ньому один ключ.

## Абстракція рушіїв

Версії слайсерів мінятимуться, а майбутні принтери можуть вимагати іншого слайсера — тому рушій це змінна, а не константа.

- `engines/base.py` — контракт `SlicerEngine` і нормалізовані DTO (`SliceRequest`, `SliceResult`, `FilamentUsage`).
- `engines/orca.py` — реалізація для upstream OrcaSlicer.
- `engines/registry.py` — реєстр за кодом.

Кожен рушій інкапсулює три речі, яких зовнішній світ не бачить: **діалект CLI**, **вимоги до вхідного файлу** (репарація потрібна Orca/Bambu-родині, PrusaSlicer її не потребує) і **формат результату** (Orca/Bambu пишуть `Metadata/slice_info.config`, Prusa — коментарі `; filament used [g] = ...` у gcode). Назовні всі повертають однаковий `SliceResult`.

Додати слайсер = fetch-стадія в `Dockerfile` (розпаковка в `/opt/engines/<code>/`) + клас у `engines/` + рядок у `registry.py`. Більше нічого міняти не треба — ні тут, ні на боці викликача.

## API

| Метод | Призначення |
|---|---|
| `GET /health` | Живість. |
| `GET /engines` | Які рушії є в образі, версії, доступність. Достатньо, щоб викликач побудував випадайку вибору. |
| `GET /engines/{code}/profiles` | Профілі рушія: `machine` / `process` / `filament`, іменами виду `Snapmaker/machine/Snapmaker U1 (0.4 nozzle)`. |
| `POST /engines/{code}/slice` | multipart: `model` (файл), опційно `machine_profile`, `process_profile`, `filament_profiles` (через `;`), `scale`, `plate`. Повертає нормалізований JSON. |
| `POST /engines/{code}/inspect` | multipart: `model`, опційно `scale`. Міряє модель **без нарізки** — ~3 с проти ~20. Профілю принтера не бере: габарит не залежить від машини. |

### Габарит моделі (з 1.1)

Обидві відповіді — і `slice`, і `inspect` — несуть блок `model`: `objects[]` (по об'єкту: `size_*`, `volume_mm3`, `facet_count`, `manifold`), плюс `object_count`, `total_volume_mm3` і `size_*` найбільшого об'єкта.

**Список, а не один габарит.** У 3MF зазвичай кілька друкованих об'єктів — каталожний брелок це цуценя, два кільця й застібка. Вони друкуються й пакуються окремо, тож коробка має задовольнити кожен плюс їхній сумарний об'єм; розмір їхньої розкладки на столі — артефакт компонування, а не властивість товару.

Джерело — сам рушій, `orca-slicer --info`, а не власна геометрія. Три речі, на яких це ламається:

1. **`--info` падає з `return -24`** на сирому Bambu-проєкті. Потрібні ті самі `--allow-newer-file --no-check`, що й для нарізки, **і** попередня репарація — та сама, що описана вище.
2. **Друкує окремий блок на кожен об'єкт**, повторюючи ті самі імена ключів під заголовком `[файл]`. Плаский розбір у один словник лишає **останній** об'єкт: на брелоку це давало 6 мм застібки замість 49 мм цуценяти. Звідси `_info_blocks()`.
3. **Координати в блоках локальні для об'єкта**, симетричні навколо нуля, без трансформацій розкладки. Звести їх в один загальний габарит із цього виводу неможливо — ще один аргумент за список.

`--scale` рушій до `--info` не застосовує, тож сервіс множить сам: лінійно для розмірів, у кубі для об'єму.

Помилки: `404` — невідомий рушій, `503` — рушій недоступний у цьому образі, `422` — нарізка не вдалася (у `detail` є `exit_code` і хвіст лога — **обох потоків**, бо причину відмови Orca пише в stderr, а не в stdout).

## Збірка й запуск

```bash
docker build -t fourd-slicer-service:dev .          # версія рушія — ARG ORCA_VERSION
docker run -d --name slicer -p 127.0.0.1:8077:8000 fourd-slicer-service:dev
curl -s http://127.0.0.1:8077/engines
```

Образ багатоетапний: AppImage тягнеться з GitHub на етапі збірки за `ARG ORCA_VERSION`, тож у git не лежить нічого важкого. Оновлення версії — `--build-arg ORCA_VERSION=2.4.3`.

`libopengl0`, `libsm6`, `libice6` у списку пакетів **обов'язкові**: без `libOpenGL.so.0` обгортка `orca-slicer-env` відмовляється стартувати, без `libSM.so.6`/`libICE.so.6` бінарник не лінкується (раніше вони приходили транзитивно з `xvfb`, який у фінальному образі не потрібен).

## Перевірені результати

Усі три моделі з каталогу, подані **без попередньої репарації** (сервіс лагодить сам) і **без машинного профілю** — тобто на профілі Bambu, зашитому в сам файл:

| Файл | Філаментів | Вага | Час друку | Плит |
|---|---|---|---|---|
| `CorgiAMS.3mf` | 3 (PLA `#FFFFFF` 97.39 г, `#F99963` 83.21 г, `#000000` 7.44 г) | 188.05 г | 15 год 7 хв | 1 |
| `Knitted_Puppy_Keychain.3mf` | 2 (PLA `#D1982E` 10.91 г, `#000000` 0.35 г) | 11.26 г | 1 год 30 хв | 2 |
| `Esun_Filament_Spool_octagon.3mf` | 1 (ABS 165.08 г) | 165.08 г | 8 год 21 хв | 2 |

Кількість філаментів збігається з розкладкою по екструдерах у `Metadata/model_settings.config` кожного файлу. Повний цикл запиту для CorgiAMS — близько 23 секунд.

### На профілі Snapmaker U1 — інші цифри, і різниця величезна

Той самий `CorgiAMS.3mf` із `machine_profile=Snapmaker/machine/Snapmaker U1 (0.4 nozzle)` і `process_profile=Snapmaker/process/0.16 Optimal @Snapmaker U1 (0.4 nozzle)`:

| Профіль | `#FFFFFF` | `#F99963` | `#000000` | Разом | Час друку |
|---|---|---|---|---|---|
| Bambu A1 (із файлу) | 97.39 г | 83.21 г | 7.44 г | **188.05 г** | 15 год 7 хв |
| **Snapmaker U1** | 16.54 г | 23.28 г | 2.25 г | **42.07 г** | **4 год 1 хв** |

Різниця в 4.5 раза — не похибка, а **прочищення**. Розбір g-code із прогону на A1 сходиться точно з тим, що звітує слайсер:

| | мм філаменту | г | частка |
|---|---|---|---|
| Укладено в деталь (рух по XY) | 17 356 | 52.6 | 28 % |
| Пролив на зміні кольору (чисте E) | 44 693 | 135.4 | **72 %** |
| Разом = `used_g` слайсера | 62 049 | 188.05 | |

420 змін інструмента × матриця проливу до 608 мм³ на перехід — три чверті філаменту йшло у prime tower. На U1 із його тулченджером проливу практично немає, у чому й полягає сенс машини.

**Практичний висновок: ціну не можна рахувати на цифрах без машинного профілю.** Розрахунок собівартості на 188 г замість 42 г завищив би її приблизно вдвічі.

## Відоме обмеження: `--scale` непридатний

Прапорець `--scale` масштабує **кожну деталь навколо її власного центру**, не розсуваючи їх. Для збірок із багатьох деталей (у CorgiAMS їх 13 — тіло, вуха, очі, ніс, лапи) це не збільшує модель, а деформує її: деталі роздуваються й перекриваються.

Виміряно на `CorgiAMS.3mf` при `--scale 1.5`: `volume` виріс рівно в 3.375 раза (=1.5³, тобто сума об'ємів деталей правильна), `size_x` — рівно в 1.5, але `size_y` лише в 1.29, а `size_z` в 1.27. Через перекриття нарізана маса зросла лише на 19% замість очікуваних ~+125%; `max_z_height` при масштабах 1.0/1.25/1.5 дав 59.56 / 63.56 / 67.56 — приріст лінійний (+4 і +8 мм), а не пропорційний.

Параметр `scale` у API поки передається в рушій як є. **Не покладатися на нього.** Запропоноване рішення (не перевірене): масштабувати самотужки, домножаючи матрицю трансформації build-item'а в `3D/3dmodel.model` — ми й так переписуємо архів у репарації, тож це природне розширення, воно детерміноване й масштабує збірку цілком.

## Що ще не зроблено

- **Філаментні профілі U1 ще не передаються.** Машинний і process уже працюють (див. вище), а `filament_profiles` поки лишається порожнім — нарізка бере філамент із самого файлу. Впливає на температури й на потік, тобто на час друку більше, ніж на грами.
- Прив'язки «філамент у каталозі викликача → профіль філаменту рушія» сервіс не робить і робити не повинен: пресети машинозалежні (`Snapmaker PLA Basic @U1` ≠ `@U1 0.6 nozzle`), тож зіставлення — справа того, хто веде каталог.
